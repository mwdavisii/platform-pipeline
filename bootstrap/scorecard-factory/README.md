# scorecard-factory

The platform-owned home of the risk scorecard: the workflow that classifies how much human review each pull request on a vibe-coded app needs, and the trusted inputs it reads. **It classifies; it does not gate.** Drift, Gate 1, the preview probe and Gate 2 stay exactly as they are. The scorecard can only add human attention.

App authors have no write access here. Everything an app could otherwise influence (its tier, its purpose, its accepted findings, its confirmed N/A requirements, the thresholds) lives in this repo, and every change is a reviewed pull request on a protected `main`.

## What is here

| Path | What it is |
|---|---|
| `.github/workflows/scorecard.yml` | The workflow app repos run on every pull request |
| `.github/actions/intake/` | A composite action that copies the inputs for the calling repo out of this repo. The runner downloads it at `@main`, so the job reads trusted data without a token |
| `config/scorecard.yaml` | Tier and classification to ASVS level, the level floor, the triggers, the Gate 1 checks, the reviewer teams, the review agent's model, gateway and budget |
| `config/registration.yaml` | `registration-rules/v1`: the minimum tier and classification the portal computes for a registration from the repo itself (no spec means `high` and `confidential`). The scorecard reads it too, for T-21. Security owns it. A change is a reviewed pull request. |
| `intake/<owner>/<repo>.yaml` | The app's `tier`, `purpose`, `owner` and `data_classification`: `intake/v1`, or `intake/v2` as the golden road portal's writer records it (the owner of record is a portal person, plus who registered and approved it, when and why, and a review date). The only source of the purpose. No intake record means `security_review` (T-8) |
| `bindings/README.md` | Frozen. Bindings moved to `golden-road-deploy` (`apps/<owner>/<repo>/<env>/bindings.yaml`); `factory-check` refuses any other file under `bindings/` (see `bindings/README.md`) |
| `na/<owner>/<repo>.yaml` | ASVS requirements a person confirmed do not apply (see `na/README.md`) |
| `suppressions/<owner>/<repo>/*.json` | Accepted scorecard findings, at most 90 days each (see `suppressions/README.md`) |
| `.github/workflows/factory-check.yml` | This repo's own check: on every pull request here it loads the config and every record with the scorecard's own loaders, so a typo can't send an app to "not assessed". The ruleset requires it |
| `.github/CODEOWNERS`, `.github/rulesets/main.json` | Platform review for everything; security review for `intake/`, `suppressions/` and `na/`; a protected `main` |

The scorecard code itself is not here. It ships inside the platform's builder image, pinned by digest in `BUILDER_IMAGE` at the top of `scorecard.yml`, together with the ASVS 5.0.0 requirements and the review prompts (each checked by SHA-256 when loaded). Nothing the workflow runs comes from the pull request.

## What a run does

Seven jobs. Their checks are named by the job, so on an app repo that calls this workflow from a job named `scorecard` they are `scorecard / precondition` and so on.

1. **`precondition`**: refuses anything but a `pull_request` event, a draft, or a fork PR, then checks that the run's merge commit was made against the pull request's current base (`edited` can arrive before GitHub recomputes the merge ref, so the run could hold a merge commit made against the old base: the commit's first parent must be the base branch's tip or in its history, by the compare API, and an exact match is not used because the base branch moves; a **re-run does not clear this**, since it reuses the same commit: push again, close and reopen the PR, or edit it), then waits (up to 45 minutes, costing runner minutes, not tokens) for the Gate 1 checks listed in `config/scorecard.yaml` to finish on the PR's head commit, and checks them with `scorecard precondition`. Any reason here means "not assessed": a failure, never a skip, and no model call.
2. **`assess`**: checks out the merge commit the run started with (`ref: github.sha`, two parents, no stored credentials), then runs `scorecard assess`, the review agent. Its container gets the checkout, the factory inputs, the event's draft, head and base fields, and one environment variable: the gateway credential. It has no GitHub token and no shell; `scorecard assess` refuses to start if any runner variable reaches it.
3. **`score`**: first checks that the factory inputs it downloaded are the ones `assess` read (a digest of the factory inputs, published by `assess` as a job output, so a merge here between the two jobs can't mix two versions), then recomputes every deterministic signal from the same checkout, reads fresh Gate 1 conclusions, checks the assessment is the exact file `assess` wrote (by its SHA-256, also a job output), and runs `scorecard run`. The job summary is the full scorecard.
4. **`report`**: sets the `scrutiny:<level>` label, updates the scorecard comment, and requests the reviewers named for the level. A failed label or comment fails the job; a failed review request is only noted.
5. **`level: <level>`**: the level, in the PR's check list, from a run the author can't edit. **Read the level here**, not from the label or the comment, which anyone with write access can change. When `score` fails, the skipped `level` job may show as `level: ` with no value: no value means not assessed, and `assessed` is the check that matters.
6. **`findings`**: fails on a high or critical deterministic finding (listed under Findings in the comment) and when `score` did not succeed. It reads only the `score` job's outputs. The app's `scorecard-findings` ruleset requires it, and that ruleset is the app's only ruleset with a bypass: an admin (the platform team on an org) can merge past it on the PR, and GitHub records each such merge as a bypass. Medium and low findings, and the reviewer's findings, never hold a merge.
7. **`assessed`**: passes only when every job above except `findings` succeeded (a held PR is still assessed). It is the check the `main` ruleset requires by name. It also writes the level into its own job summary. **The authoritative level is the one in the latest `assessed` run's summary (or the newest `level: <level>` check)**: the level is in a check's name, so after a re-run that gives a different level, the older `level: standard` check stays on the same commit next to the new one.

Every pull request event that can change the diff runs the whole workflow again: opened, pushed to, reopened, marked ready, and edited (which includes a base branch that was retargeted, so a level worked out against `staging` is not kept after the base moves to `main`). A PR is never skipped because its head commit is unchanged; each run is assessed again in full, and a newer run cancels an older one.

A PR that was not assessed stays failed until the author pushes again or someone uses **Re-run all jobs** once Gate 1 is green: a workflow can't be started by another check finishing.

## The gateway credential

`GATEWAY_AUTH` at the top of `scorecard.yml` picks how the agent reaches the model gateway named in `config/scorecard.yaml`:

- **`oidc` (preferred).** The job asks GitHub for an OIDC token with the audience `GATEWAY_OIDC_AUDIENCE`. The gateway validates it, must accept only tokens whose `job_workflow_ref` is exactly `<org>/scorecard-factory/.github/workflows/scorecard.yml@refs/heads/main` (so `.../workflows/scorecard.yml@refs/heads/main` of this repository and no other workflow, branch or repository) with `event_name == pull_request`, and enforces a per-repo daily budget. No secret exists anywhere. Whether Dependabot-triggered runs get an OIDC token at all is a proof item.
- **`key` (accepted fallback).** A scoped, budget-capped gateway key in the app repo's `SCORECARD_GATEWAY_KEY` secret. **Anyone with write access to the app repo can read it** (a workflow they write can print it), so the key must be limited to the reviewer model and capped in spend, and rotated when people leave.
- **The model name, in both modes.** The `SCORECARD_GATEWAY_MODEL` secret holds the name the gateway expects (an APIM deployment name, for example). It is not in `config/scorecard.yaml` because it can be organization-sensitive; it is sent in the request and in a `{model}` in the gateway URL, masked in the logs, and never written to the assessment, the scorecard or the comment. Without it, or with characters outside `A-Z a-z 0-9 . _ -`, the PR is "not assessed".

Either way the credential is written to a file only the next step reads, which passes it to the container with `--env-file` and deletes it. The `assess` job keeps `id-token: write` in key mode too (an expression can't set permissions), where it is unused in key mode.

**Dependabot pull requests.** A run started by Dependabot reads only Dependabot secrets, not Actions secrets. In key mode, store the same key a second time as a Dependabot secret named `SCORECARD_GATEWAY_KEY` (repo or org level), or those PRs end up not assessed. Dependabot-triggered runs can read the key too (see the limits below). Their `GITHUB_TOKEN` is also read-only by default, so whether `report` can label and comment on them is a proof item.

## Changing things

- **Onboard an app:** the app's owner registers it in the golden road portal (or their agent runs `golden-road register`, which prints the link). An admin approves it there, and the portal's writer adds `intake/<owner>/<repo>.yaml` as `intake/v2` by pull request, which merges once `factory-check` passes. Then require the workflow on the repo. Records added by hand stay `intake/v1`.
- **Accept a finding:** add a suppression file; **confirm an N/A:** add an `na/` entry. Both need security review.
- **Change thresholds, triggers, the model or the budget:** edit `config/scorecard.yaml`. `0` means no limit (for `max_total_tokens` and `max_run_seconds`); the assess job's own timeout still stops a stuck run. A `max_run_seconds` a little below the job timeout (at most 14100; for example 14000) keeps partial results: unfinished batches become `needs_human` (T-14). With `0`, a run killed by the job timeout writes no assessment (not assessed, fails closed). `scorecard run` refuses an assessment whose model version or prompt version isn't the one configured here. When `SCORECARD_GATEWAY_MODEL` changes, raise `agent.model.version` in the same change. `agent.model.version` must not contain the deployment name; the scorecard refuses it. Set `agent.model.temperature: null` if the model rejects a temperature (the gateway returns HTTP 400); an empty `temperature:` also means null; the default is 0.
- **Batching and `agent.batching.max_turns`:** each batch gets at most `max_turns` model calls. Two calls before the end the model is told to submit now (unchecked requirements as `needs_human`), and the last call forces the `submit_assessment` tool. A batch can still fail with "no valid submission" when the gateway ignores or rejects a forced `tool_choice` (for example Anthropic with extended thinking), and with "invalid output after one correction (<kind>)" when the forced submission is invalid; both leave the batch `needs_human` (T-14), but this should be rare. The reason names the kind of the last invalid submission (`too_long`, `not_json`, `schema`, `coverage`, or `finding`) and, when the provider said that reply hit the output cap, ends with "reply cut off at max_tokens_per_call" (the correction tells the model to submit less, too). A cut-off submission means `agent.budget.max_tokens_per_call` is too low: raise it (the schema allows up to 65536). The reason never quotes the model.
- **Re-review triggers (T-17, T-18, T-19):** T-17 fires when `builder-spec.json` raises `resources_tier` (`default` < `medium`; a new spec above `default` counts), T-18 when it changes `app_type` (the builder picks the base image and runtime from it), and T-19 when the change has more than `large_change.lines` changed lines (added plus removed) or more than `large_change.files` changed files. Their levels are in `triggers` (default `elevated`). A binary file counts as one file and no lines, and a `.gitattributes` rule that marks text as binary hides its lines (changing `.gitattributes` is T-16). If the size can't be measured, the run records an input problem (T-14) instead of T-19.
- **T-21, the change needs a higher registration:** the scorecard computes the same floor the portal does (the same files, size caps and signals as the portal's collector, with this factory's `config/registration.yaml`) from the PR's merge tree, and T-21 fires when the app's registered `tier` or `data_classification` in `intake/` is below it. The comment names what is registered, what the change needs, and the signal rules that fired. Its level is `triggers.T-21` (default `security_review`). No intake record is T-8, not T-21; an unreadable `config/registration.yaml` is an input problem (T-14) and T-21 does not fire. A reviewer decides; the owner asks for the registration to be raised in the portal after merging (nothing to fix in code). An override recorded at approval doesn't silence T-21 (the scorecard compares the record's tier and classification with the floor and never reads `floor_override`); only raising the registration does. The portal's `PORTAL_MODEL_GATEWAY_HOSTS` must equal the platform's `model_gateway_hosts` (the scorecard reads `platform.json`); otherwise the two floors can disagree. The scorecard reads each file as stored at the merge commit (a symlink is unreadable; a `.gitattributes` re-encoding does not hide anything).
- **The re-review event:** every assessed run adds `re-review-event.json` (`re-review-event/v1`) to the `scorecard` artifact. It holds the level, the floor, whether the assessment was complete, each trigger that fired with its level, summary and ref count, and the recorded-only signals `egress-removed`, `resources-lowered` and `builder-bumped`, which raise no level. It holds no refs, excerpts or model text. A run that is not assessed, or that fails, writes none.
- **Update the scorecard code:** release a new builder image and pin its digest in `BUILDER_IMAGE` (in both `scorecard.yml` and `factory-check.yml`). Builder 0.3.9 requires `large_change` and the `T-17`, `T-18` and `T-19` entries in `config/scorecard.yaml`, and older images refuse them, so change the config and both pins in the same pull request. Before pinning 0.3.11, compare each `intake/` record with the floor computed from its repo's main branch (the same rules as T-21): an under-registered app will be at `security_review` on every pull request until its registration is raised in the portal. Builder 0.3.11 requires `config/registration.yaml` and the `T-21` entry in `triggers`, and accepts `intake/v2`'s floor fields; older images ignore the file, refuse the `T-21` entry and refuse records that carry those fields, so add the file, the `T-21` entry and both pins in the same pull request.
- Every edit takes effect for every app repo at its next pull request, because the workflow and the intake action are read from `main`.

## Central review

Per-app mode is the default and is what the sections above describe: each app repo calls `scorecard.yml`, so each app repo holds the gateway secrets. Central review runs the same review in one place. A scheduled poller in this repo picks up the ready pull requests of every registered repo and starts one assess run per PR head, in this repo's environment `scorecard` (the only place the gateway secrets and the App key exist). A scorecard GitHub App posts the checks, the label and the comment. The app rulesets pin `scorecard / assessed` to that App's id. Per-app mode keeps working unchanged until the App exists, and central review does nothing unless the repository variable `SCORECARD_APP_ID` is set **and** `config/scorecard.yaml` has a `central:` section. Even then it assesses only the repos whose intake record says `scorecard: central` (see "Per repo" below). The setup steps are in `docs/setup/personal-poc.md` section 16.

**The flow.**
1. The poller, `scorecard-poll.yml`, runs every five minutes on `main` only. For each repo with a record in `intake/`, it mints a read token for that one repo, lists the open pull requests, and decides for each head: skip (a draft, a run in flight, already reported), mark (a fork, a red Gate 1, a run that never finished), or dispatch.
2. To dispatch, it posts a queued `scorecard / assessed` check run as the App on the PR head, then starts `scorecard-assess.yml` with `workflow_dispatch` (inputs `repo`, `pr`, `head_sha`, `check_run_id`), at most `max_in_flight` at a time across the factory, the oldest-updated PR first.
3. `scorecard-assess.yml` has four jobs. `precondition` reads the PR (it must be open, mergeable, and still at that head), checks the merge commit's parents and base, and waits for Gate 1. `assess` checks the merge commit out as data (a contents-read token, no stored credentials) and runs the review agent in the pinned builder image with the gateway credential. `score` recomputes the signals and the level. Last comes `report`: the report job is the only job that writes.
4. The report job mints the only write token (Checks, Pull requests and Issues write, for the one repo) and first verifies that the check run it was given is the App's own `scorecard / assessed` for this head. It then sets the label, the reviewers and the comment, posts `scorecard / level: <level>` and `scorecard / findings`, and last sets `scorecard / assessed` to the result of the whole run. `scorecard / findings` fails on high or critical deterministic findings and when a head wasn't assessed; it is required by the app's `scorecard-findings` ruleset, which an admin (the platform team on an org) can bypass on the PR. A newer push to the same PR cancels the older assess run.

**The App.** Permissions: Checks: Read and write; Contents: Read-only; Issues: Read and write; Pull requests: Read and write; Commit statuses: Read-only (Gate 1 entries can be commit statuses); Metadata: Read-only. No webhook. Install it on the app repos only, on "Only select repositories". The App is not installed on scorecard-factory: nothing uses it there, because the poller dispatches with this repo's own `GITHUB_TOKEN`. Every job mints its own installation token at its start (they last an hour, and an assess run can take longer); the assess job's token is used only for the checkout, before the agent starts. Each token covers one repository and only the permissions its step names, and `golden-road app-token` refuses a grant broader than that.

**Secrets and variables.**
- The environment `scorecard` (deployment branches: `main` only) holds `SCORECARD_APP_KEY` and the gateway values `SCORECARD_GATEWAY_KEY`, `SCORECARD_GATEWAY_MODEL` and, if used, the two Access values. Only the two central workflows read it, and a factory PR branch can't enter the environment.
- `SCORECARD_APP_ID` is a repository variable (it is not a secret). An environment-scoped variable can't be read in a job-level `if`, and that `if` is what keeps the poller from starting a runner when central review is off.
- The key reaches only the builder image, as an environment variable of one container, and is never printed or written; the token the image mints is written to a 0600 file and masked.

**Settings.** `central: {max_in_flight: 4, assess_timeout_minutes: 360}` in `config/scorecard.yaml`. `max_in_flight` (1 to 20) caps assess runs in flight across the factory. `assess_timeout_minutes` (at least 340) is how long a queued check may sit before the poller closes it and tries again; it has to exceed the assess workflow's job timeouts added together (30 + 240 + 30 + 10 = 310 minutes). There is no poll interval setting: the schedule is the cron in `scorecard-poll.yml`, changed by a factory pull request, and `poll_minutes` in the config is refused. Five minutes is GitHub's minimum, and scheduled runs can be delayed or dropped under load.

**What `external_id` records.** The queued or marking check run's `external_id` is `v1:<kind>:<fingerprint>:<attempt>`. The fingerprint is 16 hex characters of the base branch, the title and the body, so a retarget or an edit is assessed again, like `edited` is in per-app mode. The kind says what happened: `queued` (an assess run was started), `fork`, `final` (runs never finished, or three retries did not help; it stays failed until a new push), `gate1` and `retry`. A `gate1` mark (Gate 1 was red) is looked at again every tick, so a head whose Gate 1 turns green is then dispatched. A `retry` mark is written when the dispatch failed, and by the report job for an outcome that may pass later (GitHub's merge commit or the base branch not ready, Gate 1's wait or read not running, the factory changing between jobs); the poller dispatches the head again after ten minutes, up to three tries, then marks it `final`. A conflict, a moved head and a red Gate 1 are not retried: they need a push. A head with any other kind and the same fingerprint is not touched again. The check's summary records the queued time, and a check whose age can't be read counts as in flight, never as stale.

**Per repo.** An optional field of the intake record, `scorecard: central` (valid in `intake/v1` and `intake/v2`; absent or `per-app` means the app's own caller), says which repos the poller assesses. An app is migrated one at a time by a factory pull request that adds the line, so an app that still calls `scorecard.yml` is never reviewed twice. `scorecard-assess` refuses a repo whose record is not marked, even when started by hand. A registration approved after central mode is on is written by the portal's writer without the field: add it by a factory pull request, or that app's pull requests get no review (the kit writes no `scorecard.yml` caller in central mode). The poll summary lists the repos it skipped as per-app.

**Forks and drafts.** Forks are reviewed by a maintainer: the poller marks a fork PR once with "not assessed: pull requests from forks are reviewed by a maintainer". A draft gets no check at all (per-app mode fails `assessed` for a draft); `golden-road remediate` tells the author to mark it ready.

**Re-runs.** The Re-run button on an App's check run does nothing, because the App has no webhook. The way to assess again is to push again. On the factory's assess run, Re-run is for factory maintainers only: it rewrites the same check run.

**Artifacts and the level check.** The `scorecard-assessment` and `scorecard` artifacts are in the factory run. If this repo is private, app developers can't open it, so the `scorecard / level: <level>` check carries the redacted `scorecard.md` as its text (cut to 60,000 characters; the API limit is 65,535), and its `details_url` is the factory run. Reading those artifacts through that `details_url` is planned work for the portal's collector; until then the collector sees no artifacts for a pull request that central review assessed.

**The gateway binding.** With `GATEWAY_AUTH: oidc`, the gateway sees a token whose `job_workflow_ref` is `<org>/scorecard-factory/.github/workflows/scorecard-assess.yml@refs/heads/main`, whose `event_name` is `workflow_dispatch`, and whose environment is `scorecard`. Bind the gateway's rule to those values instead of the app repo's workflow.

**What it costs.** Every job that enters an environment creates a deployment record, so a five-minute poll adds about 288 deployments a day. On a private factory on a paid plan the poller also uses about 288 Actions minutes a day. Both are zero in per-app mode, because the job-level `if` stops the job before it starts. Environments, their secrets and their branch policies need a public repo on GitHub Free, or a paid plan for a private repo.

**What it closes.** In per-app mode a job in an app repo can post a check named `scorecard / assessed`, and the check comes from the Actions app (15368), the same as the real one. In central mode the rulesets pin `scorecard / assessed` to the scorecard App's id (`scripts/configure.py --scorecard-mode central --scorecard-app-id <id>` rewrites them and removes the apps' `scorecard.yml` callers), so a same-named job's check no longer satisfies them. If the App is ever uninstalled, merges block: the pin fails closed. `golden-road doctor` warns when a ruleset is not pinned, and `golden-road remediate` reads the App's comment (by its App id) and says "push again" for a failed App check.

**Scheduled workflows stop after 60 days without activity.** GitHub disables the scheduled workflows of a public repo after 60 days without repository activity, and the poller then stops without a failure: pull requests just never get an assessment. Check with `gh api repos/<owner>/scorecard-factory/actions/workflows/scorecard-poll.yml --jq .state` (`active`, or `disabled_inactivity`), and re-enable with `gh workflow enable scorecard-poll.yml --repo <owner>/scorecard-factory`. Any merged pull request to this repo's `main` keeps it alive.

## Known limits

- **A title or body edit costs a full assessment.** `edited` is a trigger (it is the event for a retargeted base), and it also fires for every title or body edit, bot edits included. Each one runs the whole workflow again and spends tokens. Anyone with write access to an app repo can therefore use up that repo's daily gateway budget, and its other PRs then fail safe to `elevated` (T-14, the gateway refused the call). The concurrency group cancels older runs, which bounds the cost of a burst but not the total. The control is the gateway's per-repo budget and an alert on it; a later change could skip edits that changed neither the base nor anything the scorecard reads.

- **On a personal account the checks can be imitated.** Rulesets that require workflows need an organization on an Enterprise plan. Where the app repo calls this workflow itself, a pull request can edit that caller, and a job in the app repo can post a check with the same name (every Actions check comes from the same app). The level check, the summary and the `scorecard` artifact of this workflow's run are the record; code-owner review of `.github/` in the app repo is the control.
- **Network egress is not enforced on GitHub-hosted runners.** The agent's tools are read-only and it has no shell, but nothing stops the container reaching other hosts. A runner group restricted to this workflow, with egress only to the gateway and the package registries, closes that.
- **No cache.** Each push is assessed once; a re-run spends tokens again. An app repo's workflows can write to its Actions cache, so a cached assessment could be planted.
- **Commit messages are scanned only up to the API's cap.** The injection pre-scan reads the PR's commit messages with `pulls/<n>/commits`, which returns at most 250 commits; the scan never fetches more, so a message beyond the 250th is not scanned (the file contents and the diff are, in full).
- **The concurrency group is shared by name.** A workflow in the app repo that picks the same group name (`scorecard-factory-<PR number>`) could cancel or hold a run: denial of service only, since the PR is then not assessed and stays failed.
- **Dependabot-triggered runs can read the key too.** The Dependabot secret has the same exposure as the Actions secret: anyone who can make Dependabot run a workflow of their choosing (write access) can print it. Keep the key budget-capped and limited to the reviewer model.
- **The agent can be wrong.** Code checks that every cited line exists, and uncertainty raises the level, but a confidently wrong agent can still produce `standard`. People still review at `standard`, and the report lists the agent's passes in blocking chapters to spot-check.
- **Check names can be forged (app 15368).** Every Actions check, from any workflow in any repo, is posted by the same GitHub app (ID 15368), and Gate 1 identifies a check by its name and that app ID. A workflow in an app repo with `checks: write` can post a check run with the same name as a Gate 1 check (or this workflow's), and nothing in the checks API tells the two apart. Gate 1 and the scorecard are therefore not a defence against a malicious committer in the app repo; code-owner review of `.github/` is. Only a rule that requires a workflow by its path (an organization ruleset) closes the gap.
- **Records are keyed by repository name.** `intake/`, `na/` and `suppressions/` files are found by `<owner>/<name>`, so a repository that is deleted and re-created under the same name inherits the old record: its tier, its confirmed N/A requirements and its suppressions. Delete a repository's records in the same change that retires it. Follow-up: an optional `repo_id` (GitHub's numeric repository ID) in `intake/v1`, compared with the event's, would bind a record to the repository itself.
- **`factory-check` is a typo guard, not a security control.** A pull request runs its own copy of `factory-check.yml`, so a change to `.github/` can weaken the check in the same change. What protects the workflows is code-owner review of `.github/` and the protected `main`.
- **The copied `git` is invisible to image scanners.** The builder image carries one `git` binary copied from a build stage (the scorecard's read-only git queries need nothing else), and `dpkg` does not list it, so a scanner that reads the package database will not report it. Rebuild the builder image and release a new version whenever Debian ships a git security fix, and pin the new digest in `BUILDER_IMAGE`; the image's `git.version` label says which upstream version it carries.
