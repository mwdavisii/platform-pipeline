# portal-homelab: the golden-road portal on a home k3s cluster

A deploy kit for the personal proof of concept: Flux or `kubectl` on k3s, Cilium, `cloudflared` running in the cluster. It sits next to a verified release's `manifests.yaml` and adds what the release does not carry: the namespace, a Postgres, a migration job, the writer and the collector, the settings, and the network policies for them. The builder forbids overlays inside an app repo, so the kit lives here, outside `bootstrap/golden-road-portal/`.

| Piece | File |
|---|---|
| The release (web Deployment, Service, ServiceAccount, the builder's two network policies) | `manifests.yaml`, a release asset: you download it, it is never committed (git-ignored) |
| Namespace `golden-road-portal`, pod security `restricted` | `namespace.yaml` |
| Postgres (StatefulSet pinned by digest, PVC, ClusterIP Service, role-creating init script) | `postgres.yaml` |
| Migrations as `portal_owner` (`python -m portal.migrate`) | `migrate-job.yaml` |
| Writer (`python -m portal.writer`), holds the write App key | `writer.yaml` |
| Collector (`python -m portal.collectors`), holds the read App key | `collector.yaml` |
| Postgres, edge, writer, collector, migrate and OIDC network policies | `networkpolicies.yaml` |
| Settings (a ConfigMap generated by Kustomize) and the single-image replacement | `kustomization.yaml` |
| Secret names and keys, no values, not applied by the kit | `secrets.example.yaml` |

The writer, the collector and the migration job get their image from the release's web Deployment (a Kustomize `replacements` entry), so all four always run the same image. Every container uses the release's restricted context: non-root, read-only root file system, no service account token, all capabilities dropped, seccomp `RuntimeDefault`, and limits. Postgres runs the same way as the image's own `postgres` user (uid 70).

## What you set up yourself

### 1. Authentik (OIDC)

Create an OAuth2/OpenID provider and an application for the portal:

- Client type confidential. Redirect URI (strict): `https://viber.mwdavisii.com/auth/callback`.
- Scopes `openid profile email`, and a `groups` claim in the ID token (the default scope mapping `groups` in the `profile` scope does this; the portal reads the claim named `groups`).
- Signing key: an RSA key, algorithm RS256 (the portal's default; `none` and HMAC are refused).
- Groups `golden-road-admins` (admin) and `golden-road-ops` (ops). Everyone else who signs in is a contributor.
- Put the issuer URL (`https://<authentik host>/application/o/<slug>/`) in `kustomization.yaml` as `PORTAL_OIDC_ISSUER`, and the same **host** in `networkpolicies.yaml` as the `matchName` of `golden-road-portal-oidc-egress`. Put the client id in `PORTAL_OIDC_CLIENT_ID` and the client secret in the `golden-road-portal-secrets` Secret.

### 2. Two GitHub Apps (spec P7), each installed on the `mwdavisii` account

| | Read App (collector, and linking a GitHub login) | Write App (writer) |
|---|---|---|
| Repository permissions | Metadata: read. Contents: read. Actions: read. Checks: read. | Contents: write. Pull requests (`pull_requests`): write. Metadata: read. Checks: read. Actions (`actions`): read (to trace a check run to its workflow run). Administration (`administration`): read (only to read the bypass lists the writer checks). |
| Organization permissions | Members (`members`): read | none |
| Repositories | all the platform repositories | **selected: `mwdavisii/scorecard-factory` only** |
| Note | Contents, Actions and Checks read are for the planned collectors (the minimal collector uses only repository admins). Members read has no effect on a personal account (there is no organization). | |
| User authorization | the read App's OAuth client signs a person's GitHub login in. Callback URL: `https://viber.mwdavisii.com/link/github/callback` | none; no OAuth, no webhook |

Generate one private key for each. Note each App's id, and the id of each installation (the number at the end of the installation's settings URL). Put the four ids in `kustomization.yaml`, the read App's OAuth client id as `PORTAL_GITHUB_OAUTH_CLIENT_ID`, and everything secret in the Secrets below. Turn webhooks off on both.

The writer will not start until the factory's rulesets are split as the writer's bypass check requires (see "Checks after deploy").

### 3. Cloudflare tunnel and the identity header

- In the tunnel that `cloudflared` runs, add a public hostname `viber.mwdavisii.com` with the service `http://golden-road-portal.golden-road-portal.svc.cluster.local:80` (the web Service, port 80).
- The portal's generated authorization layer wants one identity header with the single role `portal` on every request, anonymous ones included. Add a **Request Header Transform Rule** for `viber.mwdavisii.com` that sets `X-Platform-Roles: portal`. A *set* replaces any copy the client sent. If your rule type only adds, first add a rule that removes the client's `X-Platform-Roles` and then one that sets it. The header's name must be the `identity_header` of the release you deploy (`_platform/authz-policy.json` in the portal repo at the release's commit).
- The portal ignores that header for people: who may do what comes from the OIDC groups. The header only lets the request through the generated layer, and the network policies keep every other pod from sending it.

### 4. The cloudflared pods

The builder's baseline policy admits the web pods' port from the edge named in the release (`kubernetes.io/metadata.name: <edge namespace>` and a pod label). This kit adds `golden-road-portal-web-from-cloudflared` for namespace `cloudflared`, label `app=cloudflared`, so the tunnel works even if the release still holds `replace-me` as its edge. Check yours: `kubectl -n cloudflared get pods --show-labels`.

### Secrets (`secrets.example.yaml`, applied by you, never by the kit)

| Secret | Key | Variable it becomes | Used by |
|---|---|---|---|
| `golden-road-portal-secrets` | `PORTAL_OIDC_CLIENT_SECRET` | same | web |
| | `PORTAL_GITHUB_OAUTH_CLIENT_SECRET` | same | web |
| | `PORTAL_DATABASE_URL` (as `portal_web`) | same | web |
| `golden-road-portal-writer` | `PORTAL_DATABASE_URL` (as `portal_writer`) | same | writer |
| | `write-app.pem` | a file; `PORTAL_WRITE_APP_KEY_FILE=/secrets/write-app/write-app.pem` | writer |
| `golden-road-portal-collector` | `PORTAL_DATABASE_URL` (as `portal_collector`) | same | collector |
| | `read-app.pem` | a file; `PORTAL_READ_APP_KEY_FILE=/secrets/read-app/read-app.pem` | collector |
| `golden-road-portal-migrate` | `PORTAL_MIGRATE_DATABASE_URL` (as `portal_owner`) | same | migration job |
| `golden-road-portal-postgres` | `POSTGRES_PASSWORD`, `PORTAL_OWNER_PASSWORD`, `PORTAL_WEB_PASSWORD`, `PORTAL_WRITER_PASSWORD`, `PORTAL_COLLECTOR_PASSWORD` | same | Postgres init |

The database roles are `portal_owner` (owns database `portal`, runs the migrations), `portal_web`, `portal_writer` and `portal_collector`. The init script creates them once, on an empty volume, with the passwords from `golden-road-portal-postgres`; changing a password there later does not change the role (use `ALTER ROLE`). Postgres holds the four role passwords as environment variables of its pod (acceptable for a homelab; a Secret mounted as files would be the stricter choice). The web pod never gets the write key and the writer never gets the OIDC secret.

## Verify the release

Do this for every release, before you apply it. The contract is `docs/enforcement.md`, "Deploy-owner verification contract"; checking the signer alone is not enough, so pin the portal repository, the ref and the trigger. The portal repo is `mwdavisii/golden-road-portal`; the platform repo is `platform-pipeline` in the same account.

```bash
ORG=mwdavisii; APP=golden-road-portal; TAG=<release tag>
gh release download "$TAG" --repo "$ORG/$APP" --pattern manifests.yaml --dir deploy-kits/portal-homelab --clobber
cd deploy-kits/portal-homelab
REF=$(grep -m1 -E '^\s+image: ' manifests.yaml | sed -E 's/^\s+image: //')   # the image named in the file you will apply
echo "$REF"    # must be ghcr.io/mwdavisii/golden-road-portal@sha256:<digest>

id=(--certificate-identity "https://github.com/$ORG/platform-pipeline/.github/workflows/golden-road.yml@refs/heads/main"
    --certificate-oidc-issuer https://token.actions.githubusercontent.com
    --certificate-github-workflow-repository "$ORG/$APP"
    --certificate-github-workflow-ref refs/heads/main
    --certificate-github-workflow-trigger push)
cosign verify "${id[@]}" "$REF"
cosign verify-attestation "${id[@]}" --type https://golden-road.internal/gate-record/v1 "$REF" > gate.jsonl
have=$(sha256sum manifests.yaml | cut -d' ' -f1)
jq -s -e --arg repo "$ORG/$APP" --arg ref "$REF" --arg have "$have" '[.[] | .payload | @base64d | fromjson | .predicate
    | select(.status == "pass" and .repo == $repo and .image == $ref and .manifests_sha256 == $have)] | length == 1' gate.jsonl

# prod releases also carry a promotion attestation; verify it the same way
pid=(--certificate-identity "https://github.com/$ORG/platform-pipeline/.github/workflows/golden-road-promote.yml@refs/heads/main"
     --certificate-oidc-issuer https://token.actions.githubusercontent.com
     --certificate-github-workflow-repository "$ORG/$APP"
     --certificate-github-workflow-ref refs/heads/main
     --certificate-github-workflow-trigger workflow_dispatch)
cosign verify-attestation "${pid[@]}" --type https://golden-road.internal/promotion/v1 "$REF" > promo.jsonl
jq -s -e --arg ref "$REF" --arg have "$have" '[.[] | .payload | @base64d | fromjson | .predicate
    | select(.image == $ref and .manifests_sha256 == $have and .self_approved == false and .gate2_single_approver == false)] | length >= 1' promo.jsonl
```

Every `jq -e` must print `true` and every `cosign` command must exit 0, or you stop. What the homelab deployer does: the PoC deploys the **test** release, verified with the gate checks above (the first `cosign` commands and the gate `jq`); a test release has no promotion attestation, so the promotion block does not apply to it. A prod promotion record made in single-approver mode has `self_approved: true`, and a real deploy owner must reject it. If you want to deploy a prod release from the personal PoC anyway, accept that one recorded deviation **in writing** (a dated note in your GitOps repository naming the release and why), then deploy. Never skip a failing check silently or edit the `jq` to make it pass. `gate.jsonl` and `promo.jsonl` are scratch files: delete them. `gh attestation verify` is not part of this contract (the platform signs with cosign), so do not use it instead.

## Apply

Order matters: the namespace, then the Secrets, then everything else.

```bash
kubectl apply -f namespace.yaml
# fill secrets.example.yaml OUTSIDE this repository (a copy in your secret manager or an untracked file), then:
kubectl apply -f /path/to/your/filled-secrets.yaml
kubectl kustomize . | kubectl apply -f -          # or: kustomize build . | kubectl apply -f -
kubectl -n golden-road-portal get pods
```

With Flux: Flux builds from git, and `manifests.yaml` is git-ignored in this repository on purpose. So after verifying a release, commit the verified `manifests.yaml` together with this kit into your own GitOps repository, and point a Flux `Kustomization` at that directory. Never commit a `manifests.yaml` you have not verified, and re-verify against the committed file (its hash must still equal `manifests_sha256`). Set `force: true` on that Kustomization, or delete the migration Job before each upgrade (see "Upgrade"), because a Job's pod template is immutable. Keep the Secrets in your Flux secret tooling (SOPS or the like), not in git. The kit has no `images:` entry to maintain: the image comes from `manifests.yaml`.

The migration job retries until Postgres is up (twelve tries with a growing delay). The web, writer and collector pods fail their first start the same way and restart until the migrations have run; that is expected on the first apply.

### Upgrade

The order, every time: verify the new release, delete the finished migration Job, apply, wait for the Job, then expect restarts. A Job's pod template can't change, so the old Job must go first (with Flux you may instead set `force: true` on the Kustomization, which recreates it).

```bash
kubectl -n golden-road-portal delete job golden-road-portal-migrate --ignore-not-found
kubectl kustomize . | kubectl apply -f -
# wait for job/golden-road-portal-migrate to be Complete before you trust the new pods:
kubectl -n golden-road-portal wait --for=condition=complete --timeout=600s job/golden-road-portal-migrate
kubectl -n golden-road-portal get pods
```

Expect the web, writer and collector pods to roll to the new image at the same moment the migration runs, and to restart once or twice until it is done: a new pod that starts before the new migrations ran may fail and be restarted. That is the one chosen way; the writer is not scaled down. Migrations that were already applied are skipped, and one whose file changed after it was applied stops the run (then the Job fails and the pods stay on the old schema; write a new migration instead).

### Change a setting

After editing `kustomization.yaml` and applying, restart the pods that read it:

```bash
kubectl -n golden-road-portal delete pod -l 'app.kubernetes.io/name in (golden-road-portal,golden-road-portal-writer,golden-road-portal-collector)'
```

## Checks after deploy

```bash
kubectl -n golden-road-portal get pods                     # postgres, web, writer and collector Running; migrate Completed
kubectl -n golden-road-portal logs job/golden-road-portal-migrate      # lists 0001, 0002, 0003 on the first run
kubectl -n golden-road-portal port-forward svc/golden-road-portal 8080:80 &
curl -s -H 'X-Platform-Roles: portal' http://127.0.0.1:8080/healthz    # ok (from the port-forward you set the header yourself)
curl -si https://viber.mwdavisii.com/healthz | head -1     # 200 through the tunnel and the transform rule
curl -si https://viber.mwdavisii.com/ -H 'X-Platform-Roles: nobody' | head -1   # still the portal: the edge replaces the header
```

- **Sign in** at `https://viber.mwdavisii.com/`: you reach Authentik and come back through `/auth/callback`; the people page is for `golden-road-admins` members only.
- **Writer.** `kubectl -n golden-road-portal logs deploy/golden-road-portal-writer`. Until the scorecard factory's `main` ruleset is split into a checks ruleset and a review-only ruleset (`main-review`, the one ruleset the write App may bypass, by pull request only), the writer prints `writer: refusing to start: ...` with the reasons and exits 3, and the pod restarts in a loop. That is the safe outcome: do not weaken the check to make it pass. Fix the factory's rulesets (the factory's own docs), and the next restart runs. Exit code 2 means a missing or bad setting or key: the message names the variable and never prints a key.
- **Collector.** Its log line `collectors: repo_admins: N rows` appears every five minutes. A `failed: 401` or `404` means the read App's id, installation id or key is wrong.
- **Network.** From the writer pod nothing but Postgres, DNS, `api.github.com` and `github.com` answers; the web pod reaches only Postgres, DNS, GitHub and the issuer host. `cilium-dbg` or Hubble shows drops if a host is missing.
